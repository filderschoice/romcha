# ドキュメント整合性レビュー手順

このスキルは**リポジトリ内のドキュメントを読み合わせて乖離を検出し、最適化・最新化するまで**を対象とする。
成果物はMarkdownファイルの変更であり、**アプリケーションコードは1行も変更しない**（コードの課題を見つけた場合は
`docs/records/managed/BACKLOG.md` へ起票し、実装は別途行う）。

記録ファイルの書き方（ID採番の衝突確認・必須キー・YAMLの体裁・改行コード）は
[`docs/records/spec/FORMAT.md`](../../../docs/records/spec/FORMAT.md) が唯一の参照元であり、本スキルでは
ドキュメント点検に固有の内容だけを扱う。

## 0. 前提と作業ブランチ

1. `CONTRIBUTING.md` に従い作業ブランチで実施する。自律ループ実行モードで呼ばれた場合は、
   ユーザーが指定したブランチ（多くは実行中の `feature/loop-*`）をそのまま使う。
2. 点検だけを頼まれたのか、修正まで頼まれたのかを最初に確定する。「チェックして」だけなら起票で止め、
   「最適化・最新化して」なら起票してから実施まで進む。

## 1. 点検対象の棚卸し（最初にやる）

対象と規模を把握し、**手で直してよいファイル**と**触ってはいけないファイル**を先に仕分ける。

```bash
find . -name "*.md" -not -path "./node_modules/*" -not -path "./dist/*" \
  -not -path "./*/build/*" -not -path "./*/bin/*" -not -path "./*/obj/*" \
  | xargs wc -l | sort -rn
```

| 分類 | ファイル（例） | 扱い |
| --- | --- | --- |
| エージェント指示 | `CLAUDE.md`, `.github/copilot-instructions.md`, `.github/instructions/*.md` | 点検・修正の主対象。**時点情報を持たせない**（第3節） |
| 利用者向け | `README.md`, `docs/` 配下の利用者ガイド | 実装との整合を確認して更新する |
| 履歴・経緯 | `PLAN.md`, `CHANGELOG.md` | **本文は書き換えない**（第5節） |
| 配布テンプレート | `rules/`, `docs/guidelines/`, `templates/` | 導入先の視点で整合を確認する |
| 記録（自動更新） | `docs/records/managed/*.md` | マーカー内は規約どおり更新。手で書式を崩さない（第5節） |
| 記述仕様 | `docs/records/spec/FORMAT.md` | 実運用で使われている値が定義されているかを確認する |
| スキル | `.claude/skills/*/SKILL.md` | 参照先スキル名・節番号・相対リンクが実在するかを確認する |

## 2. 機械的に検出できる乖離（まずこれを流す）

読む前に走らせる。ここで挙がったものは事実として確定しているので、判断に迷わない。

### 2.1 実ファイルとドキュメント記載の突き合わせ

ドキュメントがソースファイルやルールファイルを個別に列挙している場合、追加されたファイルが漏れる。
対象パターンは自プロジェクトの構成へ読み替える。

```bash
for f in $(ls rules/*.md docs/guidelines/*.md | xargs -n1 basename); do
  grep -q "$f" CLAUDE.md || echo "  CLAUDE.md 未記載: $f"
done
```

**「未記載」が出たら、追記する前に「そもそもここに列挙すべきか」を考える。** 個別列挙は追加のたびに更新が必要で、
実際に漏れる。列挙をやめて正本へ寄せる判断は第4節。正本側（例: `docs/records/managed/DESIGN.md`）については、
**同じコマンドで網羅性を必ず確認する**（正本と決めた側に漏れがあると、参照へ置き換えた瞬間に情報が失われる）。

### 2.2 相対リンクとアンカーの到達性

```bash
python - <<'PY'
import os, re, glob
bad=[]
for path in glob.glob('**/*.md', recursive=True):
    if any(s in path for s in ('node_modules','/build/','/bin/','/obj/','dist/')): continue
    base=os.path.dirname(path)
    for m in re.finditer(r'\[[^\]]*\]\(([^)#\s]+)(?:#[^)]*)?\)', open(path,encoding='utf-8').read()):
        t=m.group(1)
        if t.startswith(('http://','https://','mailto:')): continue
        if not os.path.exists(os.path.normpath(os.path.join(base,t))): bad.append(f"  {path} -> {t}")
print("\n".join(bad) if bad else "  リンク切れなし")
PY
```

同一ファイル内アンカー（`](#見出し)`）を追加した場合は、見出しから生成されるスラッグと一致するか確認する。
日本語見出しは記号が落ちるため、`（）` や `・` を含む見出しへのリンクは目視で確認できない。

```bash
python - <<'PY'
import re
t=open('CONTRIBUTING.md',encoding='utf-8').read()   # 対象ファイルに置き換える
heads=[h.strip() for h in re.findall(r'^#{1,6}\s+(.+)$', t, re.M)]
def slug(h):
    return re.sub(r'[^\w\s-]','',h.lower()).replace(' ','-')
anchors={slug(h) for h in heads}
for m in re.finditer(r'\]\(#([^)]+)\)', t):
    print(('OK  ' if m.group(1) in anchors else 'NG  ')+m.group(1))
PY
```

### 2.3 陳腐化しやすい「時点情報」の抽出

**セッション開始時に自動読み込みされるファイル（`CLAUDE.md` と `@import` 先）に書かれた時点情報は、必ず陳腐化する。**
本スキルの抽出元となったリポジトリでの実例では、残件数の記述が2箇所にあり、いずれも実態と異なるうえ**互いに矛盾していた**。

```bash
grep -rn "本ファイル最終更新時点\|現時点で\|残件\|件のみ\|の[0-9]件\|[0-9]件です" \
  --include="*.md" . | grep -v "docs/records/managed" | grep -v node_modules
```

検出したら、原則は**記述を消して参照先を示す**（数を書かない）。「更新すればよい」は解決にならない。

### 2.4 エージェント指示ファイル間の重複

複数のエージェント指示ファイル（`CLAUDE.md`、`.github/copilot-instructions.md`、
`.github/instructions/*.md`）がある場合、**同一の規範が複数ファイルへ複製されていないか**を見る。
見出しを突き合わせると重複が見つかる。

```bash
grep -n "^#\{2,3\} " CLAUDE.md | sed 's/.*#* //' | sort > /tmp/claude-heads.txt
grep -n "^#\{2,3\} " .github/copilot-instructions.md | sed 's/.*#* //' | sort > /tmp/copilot-heads.txt
comm -12 /tmp/claude-heads.txt /tmp/copilot-heads.txt   # 両方にある = 重複の疑い
```

行単位で重複量を測るなら、エージェント名を正規化してから比較する。

```bash
norm() { sed 's/Claude Code/AGENT/g; s/Copilot/AGENT/g; s/^[[:space:]]*//' "$1" | grep -v '^$' | sort -u; }
comm -12 <(norm CLAUDE.md) <(norm .github/copilot-instructions.md) | wc -l
```

分類の判断基準:

- **重複**: 同じ規範が複数ファイルにある。→ **「共通規約1ファイル + エージェント固有差分」へ寄せる**。
  「両方を同期し続ける」運用は二重管理であり、片方だけ更新される事故を必ず生む。
- **正本を寄せた差異**: 片方にしか無いが、それが意図的な正本の所在（品質ゲートの実行コマンド等）。
  → 解消せず、**正本の所在を1か所へ書いて両方から参照する**。所在の表自体を複製しないこと。
- **エージェント固有差分**: エージェントの機能差に由来するもの（パス限定の自動適用インストラクションの有無、
  自律ループ実行モードの対象可否、git操作の可否）。→ 固有節として明示的に分離する。

共通規約の置き場所を決めるときは、**各エージェントがそのファイルを確実に自動読み込みするか**を基準にする。
参照リンクを追ってくれる前提の設計は、追わなかった場合に規約が丸ごと無効化されるため避ける。

## 3. 人が読んで判断する観点

機械検出のあとに通読する。実際に見つかった型は次のとおり。

- **廃止済みの実装・運用が現役の仕様として書かれている**。
  変更したときのID（BL番号等）を `docs/records/managed/DESIGN.md` や `EXECUTE.md` で検索すると、
  廃止された事実の裏が取れる。
- **他プロジェクト由来の記述が残っている**。汎用ガイドラインをコピーして持ち込むと、例示が別の技術スタックのまま残る。
  汎用例のつもりなら「汎用例である」と書き、そうでなければ自プロジェクトの構成へ差し替える。
- **実運用で使っている値が仕様書に定義されていない**。記録ファイルの `区分`・`担当` のように、
  「唯一の参照元」とされた仕様書に許容値が無く、実質スキル側の記述が根拠になっていることがある。
- **同じ言い回しの過剰な繰り返し**。「Copilot・Claude Code などのAIエージェント」のような長い主語が
  1ファイルに10回以上出る場合は、冒頭で用語を定義して以降を短縮する。**意味は変えない**。
- **利用者向けドキュメントに未反映の機能**。`README.md` の機能一覧は、機能追加のたびに更新が漏れる。
  `docs/records/managed/DESIGN.md` の実装済み内容と突き合わせる。

## 4. 二重管理の判定と正本の寄せ方

**判定**: 同じ事実が2箇所以上に書かれていて、片方だけが更新され得るなら二重管理。
「実際に片方だけ古くなっていた」実績があれば確定。

**正本の選び方**:

1. 更新契機が自動化されている側（記録ファイルのように、作業のたびに更新が規約化されているもの）を正本にする。
2. 詳細度が高い側を正本にし、参照する側は「層・責務・参照先」まで圧縮する。
3. 正本へ寄せる前に、**正本側の網羅性を機械的に確認する**（第2.1節）。

**圧縮する側に残すもの**（消しすぎない）:

- エージェントがセッション開始時に知らないと誤った実装をしてしまう制約
- ビルド・実行・品質ゲートのコマンド
- 「どこを見れば分かるか」の参照先表

**参照先表の作り方**: 「知りたいこと → 参照先」の対応表にする。ファイル名を列挙するだけでは、
読み手がどれを開けばよいか判断できない。

## 5. 変更してはいけない範囲

- **`docs/records/managed/*.md` の `COPILOT_RECORDS:BEGIN`〜`END` の外側とマーカー自体**。
  マーカー内も、YAMLの書式・キー・新着順の規約（`docs/records/spec/FORMAT.md`）に従う。
- **履歴・経緯として保持する文書の本文**（`PLAN.md` の当時の検討記録、`CHANGELOG.md` と `EXECUTE.md` の過去エントリ）。
  古くなっていても書き換えない。代わりに**冒頭へ位置づけを明示し、末尾へ「現行実装との差異」節を追加**して、
  当時の記述と現行を対応付ける。「差異」節は表形式（本文の記述／現行実装／経緯のID）が読みやすい。
- **配布テンプレート（`templates/`）のプレースホルダ**（`replace-me`）。埋めるのは導入先の作業。

## 6. 起票と実施

- 起票の実務（ID採番の衝突確認、必須キー、YAMLの体裁）は `docs/records/spec/FORMAT.md` に従う。
- 区分は `品質ゲート` を使う（ドキュメントの整合性は成果物の検証手段に関わるため）。
- タスク内容には**検出根拠をファイル名と行番号で書く**。「READMEが古い」ではなく
  「README.md 11〜20行目の機能一覧に○○（BL-167）が無い」と書く。
- 実施は関連性でまとめる。「実装との乖離」系と「エージェント運用ドキュメント」系のように、
  性質ごとにイテレーションを分けると差分が読みやすい。
  自律ループ実行モードで複数項目を1コミットへまとめる場合は、`CONTRIBUTING.md` の例外規定どおり
  コミット本文へ対象 `id` をすべて列挙する。
- ドキュメントのみの変更なら `EXECUTE.md` は更新しない
  （`.github/copilot-instructions.md`「記録の書き分け」）。
  `CHANGELOG.md` へ記録する。

## 7. 仕上げの検証

```bash
npx markdownlint-cli2 "**/*.md" --config .markdownlint-cli2.yaml   # 0 issues であること
git ls-files --cached --others --exclude-standard "*.md" | wc -l   # 上の Linting: N files と一致すること
file docs/records/managed/*.md                                     # CRLF になっていないこと
git diff --stat
```

- 第2.2節のリンク検査を**再実行**する（節を追加・移動すると相対リンクとアンカーが壊れる）。
- 見出しの代わりに強調（`**太字**`）で小見出しを作ると `MD036` で落ちる。`####` を使う。
- `docs/records/managed/*.md` を編集した場合は、マーカー内をYAMLとして `safe_load` できることを確認する。

## やってはいけないこと

- 機械検査（第2節）を飛ばして通読から始める。事実確認できる乖離を見落とし、印象で書き換えてしまう。
- 「未記載」を見つけて、そこに書くべきかを考えずに追記する。個別列挙を増やすほど次回の陳腐化が確実になる。
- 正本側の網羅性を確認せずに、参照へ置き換えて詳細を削る（情報が消える）。
- 履歴文書の本文を「最新化」と称して書き換える。経緯の記録という価値が失われる。
- 時点情報（件数・残件・最終更新時点）を書き換えて済ませる。次回また古くなる。
- 冗長表現の整理と称して意味を変える。主語を短縮する場合は、冒頭で用語を定義してからにする。
- `markdownlint` を通さずに完了報告する。

  実態と異なりかつ互いに矛盾、(3) 履歴文書に廃止済みの仕組みが現役の仕様として残存、

  第3節（通読の観点）を分け、第4節に二重管理の判定基準を置いた。
