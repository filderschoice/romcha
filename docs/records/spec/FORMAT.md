# records 記述ルール・記述例

[../managed/BACKLOG.md](../managed/BACKLOG.md)、[../managed/DESIGN.md](../managed/DESIGN.md)、
[../managed/EXECUTE.md](../managed/EXECUTE.md) の記述ルールと記述例の**唯一の参照元**です。
実データは各ファイルへAIエージェントが自動追記します。ユーザは各記録ファイルを直接編集しないでください。

## 共通ルール

- 記録ファイル本体はエージェント専用で、ユーザ手動編集は禁止
- `managed/BACKLOG.md` と `managed/EXECUTE.md` はYAML形式で1件ずつ追記
- `managed/DESIGN.md` はMarkdown形式の単一設計書を最新版として上書き更新
- 追記位置は各ファイルの `COPILOT_RECORDS:BEGIN` と `COPILOT_RECORDS:END` の間
- BACKLOG/EXECUTE は新着順（先頭追加）を維持し、キー名はこのファイルの定義を厳守

### YAMLとしての体裁（MUST）

`BACKLOG.md` / `EXECUTE.md` のマーカー内は、YAMLパーサ（PyYAMLの `safe_load` 等）でそのまま読み込める
状態を保ちます。1件でも壊れるとファイル全体がパースできなくなります。

- **プレーンスカラー（引用符もブロック記法も使わない値）に「半角コロン＋半角空白」を含めない。**
  YAMLがマッピングのキー区切りとして解釈し、`mapping values are not allowed here` で失敗します。
  値の1行目だけでなく、複数行にわたるプレーンスカラーの**継続行**も対象です。
- 半角コロンの直後が空白でなければ問題ありません（`C:\Windows`、`HRESULT=0` 等）。
  問題になるのは `RESULT: OK`・`状態: 進行中`・`例: file:///C:/Windows` のような書き方です。
- どうしてもこの並びが必要な場合は、次のいずれかで回避します。
  1. **ブロックスカラー化**（推奨）。折り返しの意味をプレーンスカラーと揃えるなら `>-`、
     改行をそのまま残すなら `|` を使い、次行から2字下げで本文を書きます。
  2. 全角コロン `：` を使う。
  3. 値全体を引用符（`"` または `'`）で囲む。

```yaml
    # NG: プレーンスカラーの途中に「: 」がある
    検証結果: 成功 - 実機確認の結果（RESULT: OK）を確認

    # OK: ブロックスカラー化する
    検証結果: >-
      成功 - 実機確認の結果（RESULT: OK）を確認
```

記録ファイルの改行コードはLFです。PowerShellでの一括置換はCRLF化を招くため使わないでください。

## AIエージェント更新手順（実行規約）

全エージェント共通の手順です。自律ループ実行モードでは、各イテレーションの完了時に実行します。

1. 更新前に本ファイルを参照し、対象ファイルの必須キーと型を確認する
2. `docs/records/managed/` 配下の対象ファイルの `COPILOT_RECORDS:BEGIN` と `COPILOT_RECORDS:END` の
   間だけを編集する
3. BACKLOG/EXECUTE は新規レコードを先頭に追加し、既存レコードはキー構造を維持したまま更新する
4. DESIGN は文書全体の整合性を優先して更新し、同一要件の再実装に使える実装用プロンプトとして常に最新版を保持する
5. 完了・不要レコードの削除は、各ファイルの管理ルールに従って行う。BACKLOG の項目を削除するときは、
   他タスクの `依存` から削除した `id` を外し、空になった場合は `[]` にする（削除済みの `id` が残ると、
   依存先が完了済みなのか未登録なのかを判別できなくなる）
6. 定義外キーの追加や、マーカー外の本文変更は行わない

## BACKLOG.md

### BACKLOG.md 記述ルール

必須キー:

- `id`
- `区分`
- `タスク内容`
- `優先度` (`P1` / `P2` / `P3`)
- `状態` (`未着手` / `進行中` / `ブロック` / `要確認` / `完了`)
- `担当`
- `完了条件`
- `依存` (配列。先行して完了が必要なタスクの `id` を列挙。依存がない場合は `[]`。
  BACKLOG.md に存在する `id` だけを書く。完了して削除した `id` は外す)

任意キー:

- `根拠` (判断の理由を記載。用途は下記「キーの補足」を参照)

キーの補足:

- `区分` の値は次から選びます。新しい値を増やす前に、既存のどれにも当てはまらないかを確認してください。

  | 区分 | 用途 |
  | --- | --- |
  | `不具合` | 実装が仕様どおり動作しない問題の修正 |
  | `UX改善` | 動作は正しいが、操作性・分かりやすさを改善するもの |
  | `機能追加` | 新しい機能・操作手段の追加 |
  | `性能` | 所要時間・メモリ・I/O回数の削減 |
  | `品質ゲート` | ビルド・lint・記録ファイル・ドキュメントなど、成果物の整合性と検証手段に関するもの |
  | `人手検証` | AIエージェントが自動実行できない検証（実機操作、実資格情報を用いた疎通確認など） |

- `区分` に `人手検証` を指定したタスクは、自律ループ実行モードの完了判定から除外します。
  着手の前提が実機での測定・確認であるタスクは、実装を伴うものでも一旦この区分へ変更して保留し、
  検証後に元の区分へ戻して再開します（変更理由は `根拠` へ記載）。
- `担当` の値は `AIエージェント`（Copilot・Claude Code などが実施するもの）または
  `ユーザー`（人手検証・人の判断が必要なもの）を使います。組織で役割を分けている場合は、
  その役割名（例 `Backend`）を使っても構いません。
- `状態: 要確認` は、安全性・秘密情報・外部影響に関わる不明点があり、人の判断を待つ状態を表します。
  自律ループ実行モードではこの状態のタスクを選択せず、保留したまま次のタスクへ進みます。
- `根拠` は次の場合に記載します。いずれも「なぜその判断をしたか」を後から追えるようにするためのものです。
  - 自律ループ実行モードで、仕様上の不明点に対して既定値を選択したとき（何を選び、なぜそれで安全か）
  - `区分` や `優先度` を変更したとき（特に `人手検証` へ変更して完了判定から除外するとき）
  - 完了条件を満たさないまま項目を閉じる・分割するとき

### BACKLOG.md 記述例

```yaml
- id: BL-001
  区分: 品質ゲート
  タスク内容: Rust lint/test/format を実行する
  優先度: P1
  状態: ブロック
  担当: Backend
  完了条件: cargo fmt, clippy, test 成功
  依存: []
```

自律ループ実行モードでの記述例:

```yaml
- id: BL-014
  区分: 人手検証
  タスク内容: 実機で施錠・解錠の動作を確認する
  優先度: P2
  状態: 未着手
  担当: ユーザー
  完了条件: 実機で施錠/解錠が成功し、通知で成否を判別できる
  依存:
    - BL-011
    - BL-012
```

## DESIGN.md

### DESIGN.md 記述ルール

- 形式はMarkdown
- 目的は「同一要件をAIエージェントに再実装させるための実装用プロンプト設計書」
- 文書は履歴を積み上げず、最新版を維持する
- 実装済み機能の要件・設計意図・制約・品質観点を統合して記載する
- 変更時は既存コードとの差分確認結果を反映し、要件の抜け漏れを更新する

### DESIGN.md 推奨テンプレート

```markdown
# 実装用プロンプト設計書

## 目的
- この文書の利用目的

## 対象システム概要
- 対象
- 前提環境

## 実装済み機能要件
- 要件IDと要件内容

## 設計方針
- アーキテクチャ方針
- データ設計方針
- UI/UX方針（該当時）

## 非機能要件
- 性能
- 信頼性
- セキュリティ/プライバシー

## 実装制約
- 技術制約
- 運用制約

## エージェント実装指示
- 初回実装時の出力要件
- 追加実装時の出力要件
- 要件トレーサビリティ要件
```

## EXECUTE.md

### EXECUTE.md 記述ルール

必須キー:

- `date` (`YYYY-MM-DD HH:mm`)
- `summary`
- `details.変更内容`
- `details.変更ファイル` (配列)
- `details.検証コマンド`
- `details.検証結果`

任意キー:

- `details.関連ID` (配列。対応した `BACKLOG.md` のタスク `id`。自律ループ実行モードでは必須)

### EXECUTE.md 記述例

```yaml
- date: 2026-05-12 15:45
  summary: guardrails-unified.v1.md セクション11削除と参照整合性修正
  details:
    変更内容: セクション11を削除し、関連参照を整合化
    変更ファイル:
      - rules/guardrails-unified.v1.md
      - .github/copilot-instructions.md
      - docs/guidelines/RULE.md
    検証コマンド: git diff
    検証結果: 成功 - 参照整合性を確認
    関連ID:
      - BL-001
```
